### Shipping

**You own what lands. Verify each MR independently, land only the verified run from the root, then keep your hands off the queue.**

This is the half after `playbooks/babysit.md`.

1. **Resolve the forge, then verify every MR independently.** Resolve the forge from `git remote get-url origin`. For GitLab on `git.bistek.com.br`, use `glab` as described in `../references/environment.md`. For a `github.com` remote, use `gh`. Spawn one fresh worktree-isolated background subagent per MR, not batched. Each subagent exercises the real surface against parent versus head by using the project's matching `verify-*` skill, else the "Drive a real UI" row of `../references/harness.md`. The QA host is a verification surface only where `../references/environment.md` says how to deploy. Otherwise keep its TODO. Each subagent returns `PASS`, `PASS+NOTES`, or `FAIL` and posts that verdict on its own MR. Safe means a verdict from an agent that did not write the code. CI green is not a verdict, and an approving bot review is not a verdict.
2. **Land only the contiguous verified run rooted at the bottom.** Walk up from the lowest unmerged MR and stop at the first one without a passing verdict. Both `PASS` and `PASS+NOTES` pass. A verified MR above an unverified one is not landable. Report the ceiling as an MR IID and say what breaks the chain.
3. **Re-check that each verdict still describes the patch.** Record the verdict head SHA, base SHA, and stable `git patch-id` of that MR's base-to-head diff. A rebase or base retarget rewrites SHAs and can silently invalidate a verdict without touching a check. Before landing an MR, compare the recorded patch-id with its current base-to-head patch-id. When the two patches differ only in tests, docs, or lint config, build what each lane ran. Build it twice at the verdict SHA and once at the current head. A difference is noise if the two builds at the verdict SHA also show it, or if it is an embedded commit SHA. Judge each difference, not each file, and report each kind of noise with its files. If only noise differs, that lane's result stays valid, and checks and a review of the change run fresh. Do not reuse a lane result from a dev server or from anything else with no build output. Rerun that lane. Re-verify anything else when the patch changed. When it did not, keep the code verdict but re-run mergeability and CI at the current head. Never use matching commit messages or a green check from an older SHA as a substitute.
4. **Prepare only the bottom MR.** Fetch current trunk. Rebase the lowest verified branch onto the exact trunk tip when needed, push it, and retarget only that MR with `glab mr update <iid> --target-branch <trunk>`. Re-run step 3 after the push. Do not retarget, arm, or merge descendants yet.
5. **Land one MR at a time.** If the bottom MR is mergeable now, squash it with `glab mr merge <iid> --squash --auto-merge=false --sha <verified-head> --yes`. If requirements are still running and the operator asked for merge-when-ready, arm only that MR with `glab mr merge <iid> --squash --auto-merge --sha <verified-head> --yes`. The explicit `--sha` prevents a merge if the head moved after the verdict. Wait for that MR to merge before preparing the next one.
6. **Do not read approvals as a merge verdict.** GitLab approvals show approval state through `glab api "projects/:id/merge_requests/<iid>/approvals"`. They do not prove that a merge train is armed, that a descendant is queued, that a patch verdict is current, or that the contiguous stack is safe. GitLab's `detailed_merge_status` reports its merge verdict. Confirm the active forge's state for the current bottom MR, and say the state is unknown if the active forge cannot report it. GitLab Free has no merge trains (`../references/environment.md`).
7. **Recompute after every merge.** Fetch trunk, confirm the merged SHA is present, drop the merged MR from the frozen bottom-to-top list, and inspect the new bottom MR's base, head, checks, and patch-id. GitLab may retarget a child automatically when its parent merges and its source branch is deleted, but do not assume it did. Repeat steps 3 through 6 for that one MR. Independent work stays outside this chain and ships on its own.
8. **Watch the current frontier until it merges or fails. Do not mutate the queue around it.** For GitLab, use `scripts/watch-mr/watch-mr --project <group/project> --queued-stack --stack-mrs <bottom-iid>` as an event wake, then read `glab mr view <iid> --output json` after each wake. Ignore `READY` until the MR reports merged. Check `detailed_merge_status`, its state, and its pipeline through `glab api "projects/:id/merge_requests/<iid>/pipelines"`. Hard-fail only when the MR is closed without merging, a required pipeline fails or is canceled and blocks merge after auto-merge is no longer pending, or `detailed_merge_status` reports `conflict`, `need_rebase`, or another terminal blocker. A pending pipeline or armed auto-merge is not failure. Do not use Babysit's queued `WAITING`/`merge-train` stop condition here. Hold the watch under `/loop` in dynamic mode. Report each merge and the new ceiling. If the queue stalls, diagnose before mutating.
9. **Stop at the ceiling.** When the verified run is merged, report what landed, what the next unverified MR is, and what verifying it would take. Extending the run is a new pass through step 1.

**Reply:** the verified run and its ceiling, each MR's verdict and who produced it, what you armed and how you confirmed it, what landed, and what the next gap needs.
