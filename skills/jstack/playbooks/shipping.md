### Shipping

**You own what lands. Verify each MR independently, land only the verified run from the root, then keep your hands off the stack.**

1. **Resolve the forge, then verify each MR independently before it lands.** Resolve the forge from `git remote get-url origin`. For GitLab on `git.bistek.com.br`, use `glab` as described in `../references/environment.md`. For a `github.com` remote, use `gh`. One verifier per MR, each a fresh worktree-isolated background subagent, runs the change the way a user would with the project's matching `verify-*` skill, else the "Drive a real UI" row of `../references/harness.md`, parent against head, and posts `PASS`, `PASS+NOTES`, or `FAIL` on that MR. The QA host is a verification surface only where `../references/environment.md` says how to deploy. Otherwise keep its TODO. Only a verdict from an agent that did not write the code counts, because an author checks what it meant to build. Green CI and an approving bot review are not verdicts, because neither runs the change as a user would.
2. **Land only the contiguous verified run rooted at the bottom.** Walk up from the lowest unmerged MR and stop at the first one without `PASS` or `PASS+NOTES`. The MRs below it are the run, and the top one is the ceiling. A verified MR above an unverified one waits, because it cannot land without the code below it. One whose branch neither holds nor needs that code can move onto trunk and land on its own. It needs a fresh verdict first, because its old one ran with that code beneath it and trunk does not have it.
3. **Re-check that the verdicts still describe the code.** A verdict covers a patch, and a chain rebase moves every MR above it to a new SHA without failing any check. Compare `git patch-id` at the verdict SHA with the current head before trusting an older verdict. When the patches differ only in tests, docs, or lint config, a lane's result stands if what it ran builds the same at both SHAs apart from noise. Noise is a difference that also shows up between two builds of the verdict SHA, or an embedded commit SHA. Report each kind of noise with its files, so a reader can check the call. The change itself still gets fresh checks and a review, because the old verdict never saw it. A lane with no build output, such as a dev server, cannot show this, so rerun it, and re-verify anything else that drifted.
4. **Land bottom-up, one MR at a time.** Always merge the run's lowest unmerged MR, with `glab mr merge <iid> --squash --auto-merge=false --sha <verified-head> --yes`. The `--sha` refuses the merge if the head moved after the verdict. An MR whose target is still its parent's branch merges into that branch, not trunk. Read the MR back for the result (`glab mr view <iid> --output json`), because armed auto-merge is not a merge. A landed MR reads `merged` with trunk as its target branch, not its parent's branch. Arm `--auto-merge` only on an MR whose verdict covers its current head, because it lands whatever head is ready. After a merge lands, retarget the MR whose target was the merged branch to trunk (`glab mr update <iid> --target-branch <trunk>`), move its patch onto the merge result, and push with `--force-with-lease`. GitLab may already have retargeted it when the merged source branch was deleted, so read it before you change it. The verdict covers the patch, not its commits, so step 3's patch-id rule decides whether the verdict survives. Merge it once its pipeline passes and its verdict survives.
5. **Leave the stack alone while it lands.** Step 4's move of the next MR is the only change to a branch or target, because a merge lands whatever its branch and target hold at that moment, verdict or not. Watch the run with `scripts/watch-mr/watch-mr --project <group/project> --queued-stack --stack-mrs <bottom-to-top>` under `/loop` until it reports `COMPLETE` at the ceiling. Ignore `READY` until the MR reads merged, and do not stop at Babysit's queued `WAITING`/`merge-train`, because neither means the MR landed. After each wake, read `detailed_merge_status` and the pipeline (`glab api "projects/:id/merge_requests/<iid>/pipelines"`). `conflict`, `need_rebase`, a closed MR, or a failed required pipeline is a stop. A pending pipeline or armed auto-merge is not. A target that moves to trunk when its parent merges is expected, not damage to repair. If a merge stalls, find out why before you change anything. GitLab Free has no merge trains (`../references/environment.md`).
6. **Stop at the ceiling.** Extending the run takes new verdicts, so it is a new pass through step 1.

**Reply:** the verified run and its ceiling, each MR's verdict and who produced it, what landed and how you confirmed it, and what the next gap needs.
